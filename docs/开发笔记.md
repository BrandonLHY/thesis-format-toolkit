# 开发笔记

记录开发与维护过程中踩到的坑，以及调试方法。

这些内容不属于**使用说明**（那些在 [README](../README.md)），
但对要改这个项目的人有用——尤其是那些「不看就会再踩一遍」的坑。

---

## 一、怎么可靠地查 CI 状态

这个项目有三个平台 × 两个 Python 版本的矩阵。加 macOS 任务时，
我曾连续三轮误判 CI 状态，绕了不少弯路。原因是**方法本身不可靠**。

### 三种方法的可靠性

| 方法 | 可靠性 | 问题 |
|---|---|---|
| 徽章 `badge.svg` | **低** | 只反映「最近一次运行」，且有缓存延迟。任务还在跑时显示的是上一次的结果，会让人误以为没进展 |
| 运行页面 HTML | 中 | 任务列表只渲染出前几个，其余似乎按需加载，容易漏掉失败的那个 |
| **GitHub API** | **高** | 能拿到全部任务和每个步骤的结论。缺点是匿名调用会限流（403） |

**结论：优先用 API。** 限流时等几分钟再来，不要退回徽章做判断。

### 推荐命令（API）

```powershell
$r = Invoke-RestMethod -Uri 'https://api.github.com/repos/BrandonLHY/thesis-format-toolkit/actions/runs?per_page=1' `
     -Headers @{'User-Agent'='ci-check'} -TimeoutSec 25
$run = $r.workflow_runs[0]
"$($run.head_sha.Substring(0,7))  $($run.status)/$($run.conclusion)"

$jobs = Invoke-RestMethod -Uri $run.jobs_url -Headers @{'User-Agent'='ci-check'} -TimeoutSec 25
foreach ($j in $jobs.jobs) {
  "[$($j.conclusion)] $($j.name)"
  if ($j.conclusion -eq 'failure') {
    foreach ($s in $j.steps) { if ($s.conclusion -eq 'failure') { "     失败步骤: $($s.name)" } }
  }
}
```

### 备用方法：从运行页面读步骤结论（无需登录）

运行页面的 HTML 里有 `check-step` 元素，带 `data-name` / `data-number` /
`data-conclusion` 三个属性。即使没有登录也能读到：

```powershell
$r = Invoke-WebRequest -Uri "https://github.com/<owner>/<repo>/actions/runs/<run_id>/job/<job_id>" `
     -UseBasicParsing -TimeoutSec 25
[regex]::Matches($r.Content, 'data-name="([^"]*)"\s+data-number="(\d+)"\s+data-conclusion="([^"]*)"') |
  ForEach-Object { "[$($_.Groups[3].Value)] $($_.Groups[2].Value). $($_.Groups[1].Value)" }
```

任务 ID 从运行页面的 `href="/<owner>/<repo>/actions/runs/<run_id>/job/<job_id>"` 里取。
注意页面可能只列出部分任务。

### 一个必须避免的验证脚本缺陷

写轮询脚本时，我犯过这个错误：

```powershell
# 错误写法：找不到任务 ID 时，foreach 一次都不执行，
# $allFail 保持为空，于是「没检查到任何东西」被判成了「全部通过」
foreach ($jid in $jids) { ... }
if ($allFail.Count -eq 0) { 'ALL GREEN' }
```

**验证脚本必须断言「检查到了预期数量的对象」。**

```powershell
if ($jobs.jobs.Count -ne 5) { throw "只检查到 $($jobs.jobs.Count) 个任务，预期 5 个" }
```

空集合被当成成功信号，是验证工具里最危险的一类 bug——它会让你以为问题解决了。

## 二、PowerShell 里的两个坑

### `-match` 返回的是匹配内容，不是布尔值

```powershell
$has = ($out -match '(?m)^password=.+')   # $has 是匹配到的字符串，不是 $true
```

**这条坑让我把 GitHub 凭据打印到了终端输出里**——因为紧接着就
`Write-Output "凭据可用: $has"`，把整个匹配串打了出来。

正确写法：

```powershell
$has = [bool]($out -match '...')      # 显式转布尔
# 或者干脆用 if
if ($out -match '...') { ... }
```

**涉及凭据、密钥的输出，务必先想清楚变量里到底是什么。**
更稳妥的做法是根本不要把凭据放进会参与输出的变量。

### `git credential fill` 返回的是字符串数组

```powershell
$cred = "protocol=https`nhost=github.com`n`n" | git credential fill
# $cred 是 array，4 个元素：protocol= / host= / username= / password=
```

对数组直接做正则会被 PowerShell **隐式拼成一行**（用空格连接），
于是行锚点 `^` 失效、`(?m)^password=` 永远匹配不上：

```powershell
# 错误：匹配不到
$token = ([regex]::Match($cred, '(?m)^password=(.+)$')).Groups[1].Value

# 正确：按元素筛
$token = ($cred | Where-Object { $_ -like 'password=*' }) -replace '^password=', ''
```

## 三、没有真机怎么测别的平台

以 macOS 为例。目标是**在没有 Mac 的机器上**尽量把风险测出来。
分三层，互为补充：

### 第 1 层：录制回放（测解析逻辑）

把真实平台命令的输出**结构**录下来存成夹具，喂给解析函数做确定性断言。

这个项目里对应 `tests/fixtures/fonts_macos_real.json`
（`system_profiler SPFontsDataType -json` 的输出）和 `selftest_fontparse.py`。

优点：在任意平台都能跑，还顺便覆盖畸形输入（截断的 JSON、字段为 null、
类型不对等十几种）。

### 第 2 层：环境模拟（测全套件的平台敏感性）

在任意平台把平台标识、探测结果替换成目标平台的样子，
再跑一遍**全部**套件，一次列出所有「只在那个平台上才会失败」的断言。

对应 `selftest_macos_sim.py`。

**★ 关键教训：模拟必须覆盖真机的实际状态，不能只模拟「一切正常」那种。**

这个脚本最初只模拟「`system_profiler` 正常工作、拿到真实字体家族名」。
但真机 runner 上 `system_profiler` 是**失败**的（返回合法 JSON 但 `_items` 为空），
走的是退回扫描目录那条路。模拟与真机不一致，于是问题没被提前发现，
真机 CI 连续失败三轮。

现在模拟两种环境，都要通过：

| 模式 | 含义 |
|---|---|
| `profiler` | 系统命令正常，拿到真实值 |
| `dirscan` | 系统命令失败，退回降级路径 |

### 第 3 层：真机 CI（确证夹具没脱离现实）

GitHub Actions 的 `macos-latest` runner，公开仓库使用标准 runner 不收费。

它验证的是**前两层是否忠实于真实平台**——夹具结构对不对、
模拟的环境是否与真机一致。对应 `selftest_macos_live.py`。

**为什么真机 CI 每次只暴露一个问题：** 工作流里某一步失败后，
后面的步骤会被跳过。所以修一个才能看到下一个。这正是第 2 层存在的意义——
它能一次列全，不必一轮一轮试。

## 四、字体名与文件名之间没有可靠对应关系

这条值得单独记，因为它让一个「看起来合理」的方案彻底失败。

macOS 上如果 `system_profiler` 不可用，只能退回扫描字体目录，
拿到的是**文件名**。曾想用前缀模糊匹配把这些文件名对应到字体家族名：

```
Songti.ttc  -> songti  -> 猜成 Songti SC   ✓ 猜对了
Kaiti.ttc   -> kaiti   -> 猜成 Kaiti SC    ✓ 猜对了
```

但同一套规则会：

```
Kaiti.ttc        -> kaiti  -> 撞上 Windows 字体名 KaiTi   ✗
Times New Roman.ttf -> times new roman -> 被猜成 Times     ✗
```

**根因：**
- 有些字体把多个家族打包在 `.ttc` 里，文件名只是其中之一（`Songti.ttc` 里同时有 Songti SC 和 STSong）
- 有些文件名恰好就是完整家族名（`Times New Roman.ttf`）
- 有些文件名去掉后缀正好等于另一个平台的字体名（`kaiti` == `KaiTi` 归一化后）

**结论：文件名不是字体家族名，任何启发式都是在猜。**
现在的实现是**只做精确匹配**：命中就用，命中不了就保持原名字
（Word 会自行回退，与不替换的效果一致），绝不凭空写入系统里不存在的字体名。

**更一般的教训：** 当一个修复方案连续两轮引入新问题，
应该重新审视方案本身，而不是继续加条件。这里我打了三次补丁
（整段被误标上标 → KaiTi → Times）才意识到该回退。

## 五、诊断脚本的定位：报告事实，不要把环境差异判成失败

`selftest_macos_live.py` 是**诊断**脚本，不是**把关**脚本。
它一开始把「runner 上装了什么字体」这类环境事实写成了断言，结果：

- runner 的字体列表与开发机不同 → 判失败 → CI 变红，但程序没问题
- `system_profiler` 返回合法 JSON 但 `_items` 为空 → 判失败，但解析出 0 个字体是**正确**的

**现在的原则：**

| 类型 | 处理 |
|---|---|
| 环境事实（装了哪些字体、命令是否可用） | 记为 `note`，只报告 |
| 程序契约（有输入就必须能解析出结果） | 用 `ok` 断言 |

保留的两条硬断言：
1. JSON 里**确实有字体条目**却解析不出来 → 解析逻辑有问题
2. 字体目录里明明有文件，`installed_fonts()` 却返回空 → 探测逻辑有问题
   （第 2 条正是之前那个「探测失败却伪装成成功」缺陷的形态）

## 六、跨平台断言怎么写

同一个程序在不同平台上有不同**正确**结果时，测试期望值必须跟着平台算，
不能写死。这个项目踩过两次：

| 位置 | 写死的期望 | macOS 上的正确值 |
|---|---|---|
| `验收检验.py` 第 5 节 | 输出应是「黑体 / 宋体」 | Heiti SC / Songti SC |
| `selftest_fidelity.py` 第 12 节 | 自定义预设的「楷体」生效 | Kaiti SC |

**写法：把期望值经过程序自己的解析函数算一遍再比较。**

```python
from platform_fonts import resolve_font
want = resolve_font("宋体")          # 由程序决定「宋体」在本平台应变成什么
ok("正文 = %s" % want, actual == want)
```

这样断言的是**契约**（输出应等于解析结果），而不是某个平台的**具体值**。

**另一个相关教训：** `resolve_fonts_in_preset` 的测试曾把预设结构传错
（传成嵌套字典，而函数期望 `{区域名: RegionFormat 对象}`），
导致 `getattr` 取不到属性、函数永远原样返回，**两条断言恒真、等于没测**。

写测试时要问一句：**如果我故意把被测函数改坏，这条断言会红吗？**

## 七、运行产物不要让它们进仓库

`.gitignore` 里有一类规则是「程序跑出来的文件」：`自检报告.txt`、
`macOS诊断报告.txt`、`预设.json`、`体检报告*.html`。

**踩过的坑：** `selftest_macos_sim.py` 会调用 `selftest_macos_live.py`，
后者把报告写在项目根目录。一次 `git add .` 就把这个运行产物提交进仓库了。

提交前建议看一眼 `git status`，别直接 `git add . && commit`。
最可靠的自查是 `git ls-files`——它列出真正会被上传的每个文件。

## 八、发布流程

打包、发 Release、GPL 分发义务见 [打包与发布](打包与发布.md)。

发布可以用脚本完成（`_发布.ps1`，下划线开头所以不会进仓库）：

```powershell
pwsh -File _发布.ps1 -Tag v1.2.2 -Title "v1.2.2 某某修复"
```

它会从 `_Release_v1.2.2.md` 里抽正文、从 `release/` 找对应压缩包、
调 GitHub API 创建 release 并上传附件。**已做幂等处理**，
对已发布的 tag 再跑一次不会重复创建。

**凭据从 `git credential` 读，脚本里绝不打印。**

## 附：这个项目修过的几个有代表性的缺陷

按「为什么值得记」排列：

| 缺陷 | 为什么值得记 |
|---|---|
| **探测失败被伪装成成功** | 最隐蔽的一类。`system_profiler` 返回合法但空的 JSON 时，旧实现把区段标签当成了字体名，于是字体集合非空、「探测失败就退回扫描」的兜底不触发，最终把 Windows 字体名写进文档且不报错 |
| **上标切分复制换行节点** | 文字完整性检查抓不到它——换行是节点结构不是字符。只有直接统计 `w:br` 节点数才会露馅 |
| **run 对象身份比较** | python-docx 的 `p.runs` 每次访问都重建包装对象，`is` 比较永远为真，导致刚写入的标题文字被立刻清空 |
| **字体回退链在 Word 中无效** | `w:eastAsia="宋体,Songti SC"` 被 Word 当成**一个**字体名。这个假设是被 Word COM 实测推翻的，不是推理出来的 |
| **主题字体压制具体字体名** | `w:eastAsiaTheme` 存在时会压过 `w:eastAsia`，必须先把主题属性删掉 |

共同的教训：**「看起来能工作」和「真的能工作」之间隔着实测。**
这几条里有三条是靠真机或真实文档才发现的，本地自检全都通不过关。
